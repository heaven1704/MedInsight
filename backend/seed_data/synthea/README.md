# Synthea seed data (MedInsight Step 9)

This folder contains the synthetic patient source data used by the
[`seed_from_synthea`](../README.md) management command.

## IMPORTANT — synthetic data only

Every record in this project produced by synthea seeding is **synthetic**,
generated by / in the style of MITRE's open-source
[Synthea](https://github.com/synthetichealth/synthea) patient generator. It is
**not real patient data / PHI**. No real names, contacts, or medical records are
used anywhere in the demo data.

## Files

- `patients.csv` — a Synthea-format patient demographics file (this is what the
  importer reads).
- `generate_patients.py` — a small, deterministic Python generator that writes
  `patients.csv` in exactly Synthea's CSV column layout. It exists so the demo
  works on machines that don't have Java (Synthea itself requires a JDK).

## How this data was produced (reproducible)

### Option A — real Synthea (recommended for a fuller population; needs Java 17+)

1. Download the Synthea release jar:
   <https://github.com/synthetichealth/synthea/releases>
2. Run it with CSV export enabled. Example:

   ```bash
   java -jar synthea-with-dependencies.jar \
       -p 40 \
       -r 20260301 \
       --exporter.csv.export=true \
       --exporter.csv.folder=./backend/seed_data/synthea \
       --exporter.csv.appendMode=false
   ```

   That writes `patients.csv` (and other CSV exports) into this folder. Point
   `seed_from_synthea --csv <folder>` at it.

### Option B — bundled generator (used for this environment, no Java)

```bash
cd backend/seed_data/synthea
python generate_patients.py
```

This writes `patients.csv` with the deterministic 40-patient dataset committed
here. It mirrors Synthea's `patients.csv` column header so the importer is
agnostic to which option produced the file.

> `patients.csv` as committed is already present, so you can seed without doing
> either step above. The two options above are only needed if you want to
> regenerate or enlarge the dataset.

## Synthea CSV columns consumed

The importer reads these columns from `patients.csv`:

| Column    | Used as                                     |
|-----------|---------------------------------------------|
| `Id`      | stable synthetic identifier (not stored)    |
| `FIRST`, `LAST` | patient `full_name` (`FIRST LAST`)    |
| `BIRTHDATE` | `date_of_birth` (Synthea format `YYYYMMDD`) |
| `GENDER`  | `gender` (`M` → male, `F` → female, else → other) |
| `ADDRESS`, `CITY`, `STATE` | joined into the free-text `address` |

All other CSV columns (SSN, DRIVERS, race, etc.) are present for fidelity to the
real Synthea format but are **not** imported by the demo importer.

## Mapping decisions (Synthea → MedInsight)

Synthea's base `patients.csv` has no columns for several fields MedInsight needs.
The importer makes documented synthetic decisions for those:

| MedInsight field | Source / decision |
|------------------|--------------------|
| `full_name`      | `FIRST` + `LAST` |
| `date_of_birth`  | `BIRTHDATE` (Synthea `YYYYMMDD` → ISO) |
| `gender`         | `GENDER`; `M` → male, `F` → female, other → `other` |
| `address`        | `ADDRESS, CITY STATE` rejoined from the split CSV columns |
| `phone`          | Synthea has no phone column. Derived deterministically; **all members of a household (patients sharing an address) get the same phone** so Step 4's phone+address family-matching has real signal. |
| `email`          | Derived `first.last@example.medinsight.local` (Synthea doesn't export emails in the base CSV) |
| `blood_group`    | Synthea has no blood type. Assigned pseudo-randomly from the `Patient.BloodGroup` choices as a synthetic default. |
| `allergies`      | Synthea stores these in a separate `allergies.csv` export. Assigned 0–2 curated synthetic allergies as a default here. (Importing `allergies.csv`/`conditions.csv` is future work.) |
| `medical_history`| Synthea keeps diagnoses in `conditions.csv`. A short age-appropriate history note is synthesized per patient so the Medical History tab is populated. |

## Household / family groupings

Some patients are intentionally assigned the same phone number and address so
the patient detail "Family" tab has real matches to show:

- A few co-located household clusters are linked into actual `Family` records
  (so the member list renders).
- The remaining co-located clusters are left **ungrouped** so the
  `possible-family` grouping banner has matches to offer live in a demo.
