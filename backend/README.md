# MedInsight backend — Step 9 (data seeding)

This document covers the **synthetic data seeding** added in Step 9. It explains
how to run the seed, what it creates, the dev login accounts, and the
verification checklist used before this step was considered done.

> ## Synthetic-data disclaimer
> All demo data in this project is **synthetic**, generated by / in the style of
> MITRE's open-source [Synthea](https://github.com/synthetichealth/synthea)
> patient generator. It is **not real patient data / PHI** and must never be
> mistaken for real records.

---

## Prerequisites

- Backend dependencies installed (`pip install -r requirements.txt`) and
  migrations applied (`python manage.py migrate`).
- A Synthea-format `patients.csv` — the committed one in
  `seed_data/synthea/patients.csv` is used automatically. To regenerate/enlarge
  it, see [`seed_data/synthea/README.md`](seed_data/synthea/README.md) for the
  exact, reproducible command.

## Running the seed

```bash
cd backend
# Clean out any existing patient/family/appointment/document rows, then seed:
python manage.py seed_from_synthea --flush

# For the very first run on an empty DB (no --flush needed):
python manage.py seed_from_synthea
```

Options:

| Flag | Meaning |
|------|---------|
| `--flush`       | Delete existing Patient/Family/Appointment/Document rows before seeding. |
| `--csv <path>`  | Use a different Synthea `patients.csv` instead of the default. |
| `--skip-documents` | Skip creating sample documents (faster re-seeds). |

The command is **guarded**: if patient data already exists and `--flush` is not
passed, it refuses to run (so a demo password change or manual edit can't be
silently wiped).

## What the seed creates

- **Dev login accounts** (created only if they don't already exist — existing
  passwords are never overwritten):

  | Username   | Role         | Password         |
  |------------|--------------|------------------|
  | `admin`    | admin        | `admin123!`      |
  | `dr_patel` | doctor       | `DoctorPass1!`   |
  | `dr_kapoor`| doctor       | `DoctorPass1!`   |
  | `reception`| receptionist | `ReceptionPass1!`|

- **40 patients** with demographics, blood group, allergies, and a medical
  history note, mapped from the Synthea CSV (see the mapping table in
  [`seed_data/synthea/README.md`](seed_data/synthea/README.md)).
- **2 Family groupings** (real `Family` records → the patient "Family" tab shows
  a member list).
- **Households sharing a phone/address but left ungrouped** so the
  `possible-family` grouping banner has real, clickable matches during a demo.
- **~40 appointments** spread across past/upcoming dates with a realistic mix of
  statuses (scheduled / completed / cancelled / no_show).
- **6 sample documents** (valid placeholder PDFs, `processing_status=uploaded`)
  so the document list and "Run OCR" button have something to click. OCR is
  triggered manually per document (Step 8) — the `run-ocr` action marks a
  document `needs_review` (never a 500) if the ai-service is unavailable.

## Verification checklist (used to confirm this step is done)

Seeded locally, then exercised through the live REST API and checked in every
relevant view/frontend expectation:

1. **Login** works for the `reception` / `admin` / `dr_patel` accounts.
2. **Patients list** returns 40 rows with `full_name`, `date_of_birth`, `gender`,
   `phone`, `email`, `blood_group`, `family_name`, `last_visit`.
3. **Search** `?search=Rohan` returns the matching patient.
4. **Patient detail** returns populated `allergies`, `medical_history`,
   `blood_group`.
5. **Possible-family banner** — e.g. `GET /api/patients/{id}/possible-family/`
   for an ungrouped patient returns 1–2 matches sharing a phone (verified live:
   Rohan Bose → 2 matches).
6. **Family tab** — families list shows member counts; grouped patients render a
   member list.
7. **Appointments list** shows `patient_name`, `doctor_name`, `date`, `time`,
   `status`; `/api/appointments/today/` returns today's bookings; statuses are a
   healthy mix across past/future.
8. **Documents list** returns the seeded PDFs and the media files are served as
   `application/pdf` over HTTP.
